# M7.7 — Activity Stream — Design

> **Status:** brainstormed (2026-05-12)
> **Origem:** [docs/superpowers/specs/2026-05-11-paperclip-gaps-ux-governance-design.md §4](2026-05-11-paperclip-gaps-ux-governance-design.md)
> **Estimativa total:** 3–4 dias · **Fatiado em 2 PRs:** PR-A foundation (~2 dias) + PR-B UI (~1.5–2 dias)
> **Pré-requisito:** nenhum hard. Recomendado **antes do M7.6** porque M7.6 introduz vários IPCs (pause/terminate/set-mode) que vão chamar `recordActivity()` desde o dia um.

---

## 1. Por que e o que

O Paperclip oferece "visão e controle do todo" via página `/activity` cross-cutting — único surface da sidebar do Paperclip sem equivalente nosso. Hoje temos `issue_events` (escopo issue) e `inbox` (user-facing mutável), mas nenhuma visão consolidada de "o que aconteceu na empresa hoje" capaz de responder "o que o BackendEng fez nas últimas 2 horas que não foi mensagem?".

M7.7 é **foundation**: helper central `recordActivity()` + tabela `activity_events` + página `/activity`. Uma vez que o helper existe, M7.6 (Agent Studio) e M8.5 (Goals) só ADICIONAM events novos — sem rebuild de infra.

**Princípio:** dual-write consciente. `issue_events`, `inbox_items` e `costs_log` continuam funcionando exatamente como hoje. `recordActivity()` é chamado **em paralelo** nos call sites — não substitui nada. Sem backfill retroativo (audit começa do dia em que entra).

## 2. Distinção Activity ↔ Inbox

| Aspecto | Activity | Inbox |
|---|---|---|
| Mutabilidade | Imutável append-only | Mutável (mark-read, approve, reject) |
| Propósito | Audit/history "o que aconteceu" | Work surface "o que precisa de mim" |
| Volume | Alto (todo evento) | Baixo (só ações que pedem usuário) |
| Filtros | actor_kind, action, entity_kind, agent, data | kind, requires_action |
| Dismiss | Não existe | Mark-read explícito |
| Real-time | Sim (prepend live) | Sim (já existe M5) |

**Overlap consciente:** approval triggers ambos — 1 inbox item (actionable) + 1 activity event (`approval.requested`). User aprova/rejeita → activity ganha 2º event (`approval.approved` ou `approval.rejected`); inbox item vira read.

## 3. Arquitetura

Três peças:

1. **`activity_events`** (migration 0009) — tabela única append-only, sem FK em `entity_id` (preserva audit pós-delete da entidade).
2. **`recordActivity()`** — helper central em `apps/main/src/activity/recorder.ts`. Valida payload via Zod por action, escreve row, broadcasta `ACTIVITY_NEW`. Hard cap 4KB no payload (throw em dev, trunca + `_truncated: true` em prod).
3. **Página `/activity`** — rota nova, flat-list desc por `created_at`, infinite scroll 50/chunk, filtros, search client-side, real-time prepend via `ACTIVITY_NEW`.

```
┌────────────────────┐    recordActivity()     ┌──────────────────┐
│ agents/repository  │ ─────────────────────▶ │                  │
│ issues/repository  │ ─────────────────────▶ │   activity_      │
│ projects/repository│ ─────────────────────▶ │     events       │
│ mcp/tools/*        │ ─────────────────────▶ │   (sqlite)       │
│ permissions/service│ ─────────────────────▶ │                  │
└────────────────────┘                         └─────────┬────────┘
                                                          │
                                          ACTIVITY_NEW broadcast
                                                          ▼
                                              ┌──────────────────┐
                                              │ /activity route  │
                                              │ + Sidebar item   │
                                              └──────────────────┘
```

## 4. Schema — migration `0009_activity_events.sql`

```sql
CREATE TABLE activity_events (
  id TEXT PRIMARY KEY,                              -- uuid v4
  company_id TEXT NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  actor_kind TEXT NOT NULL,                         -- 'user' | 'agent' | 'system'
  actor_id TEXT,                                    -- agent.id quando actor_kind='agent', NULL nos outros
  action TEXT NOT NULL,                             -- ex: 'agent.hired', 'issue.created'
  entity_kind TEXT NOT NULL,                        -- 'agent' | 'issue' | 'project' | 'approval' | 'session' | 'company' | 'goal'
  entity_id TEXT NOT NULL,                          -- SEM FK por design
  agent_id TEXT,                                    -- denormalizado pra filtro rápido por agente
  payload_json TEXT NOT NULL,                       -- JSON ≤ 4KB
  created_at INTEGER NOT NULL                       -- epoch ms
);

CREATE INDEX idx_activity_company_time  ON activity_events(company_id, created_at DESC);
CREATE INDEX idx_activity_entity        ON activity_events(entity_kind, entity_id);
CREATE INDEX idx_activity_agent_time    ON activity_events(agent_id, created_at DESC);
CREATE INDEX idx_activity_action        ON activity_events(action);
```

**Decisões:**

- **`entity_id NOT NULL`** porque toda action tem entity. Deleção de entity é tolerada pelo lookup do UI (tooltip "(deleted)" + click disabled).
- **`agent_id` denormalizado** mesmo quando redundante com `actor_id` — permite filtrar "tudo do BackendEng" mesmo em rows onde actor é `user`/`system` (ex.: `agent.terminated` por user → agent_id = alvo, actor_id = NULL).
- **`payload_json TEXT`** (não BLOB) — Better-sqlite3 retorna string direto; parse no repo.
- **Sem `updated_at`** — append-only ao nível de app; repository expõe apenas `insert` + `read`.
- **Numeração 0009:** confirmado via Glob — migrations atuais vão até `0008_issue_artifacts.sql` (M7.5 PR-B). O spec gaps mencionava `0008` porque foi escrito antes de M7.5 PR-B consumir esse número.

## 5. Types & action vocabulary

**`packages/shared/src/types/activity.ts`** (novo):

```ts
import { z } from 'zod';

export type ActorKind = 'user' | 'agent' | 'system';

export type Actor =
  | { kind: 'user' }
  | { kind: 'agent'; id: string }
  | { kind: 'system' };

export type EntityKind =
  | 'agent' | 'issue' | 'project' | 'approval'
  | 'session' | 'company' | 'goal';

// ~30 actions v1 — string-literal union (não enum, alinha com convenções do projeto)
export type ActivityAction =
  // Agent (10)
  | 'agent.hired' | 'agent.role_changed' | 'agent.model_changed'
  | 'agent.persona_edited' | 'agent.skills_changed' | 'agent.reports_to_changed'
  | 'agent.allowed_projects_changed' | 'agent.paused' | 'agent.resumed' | 'agent.terminated'
  // Issue (5)
  | 'issue.created' | 'issue.status_changed' | 'issue.assignee_changed'
  | 'issue.priority_changed' | 'issue.comment_added'
  // Approval (3)
  | 'approval.requested' | 'approval.approved' | 'approval.rejected'
  // Project (3)
  | 'project.created' | 'project.updated' | 'project.deleted'
  // Goal (4) — defined now, not emitted until M8.5
  | 'goal.created' | 'goal.plan_proposed' | 'goal.plan_approved' | 'goal.status_changed'
  // Session/Cost (3) — session.* emitido por turn-complete; cost.day_summary depende M8
  | 'session.started' | 'session.ended' | 'cost.day_summary'
  // Company (2)
  | 'company.created' | 'company.updated';

// Zod payload schemas — uma entry por action.
// `satisfies` força exhaustividade: TS reclama se faltar entry pra alguma ActivityAction.
export const ActivityPayloads = {
  'agent.hired': z.object({ name: z.string(), role: z.string(), model: z.string().optional() }),
  'agent.model_changed': z.object({ from: z.string(), to: z.string() }),
  // ... uma entrada por ActivityAction (~30 total) — definidas na implementação
} satisfies Record<ActivityAction, z.ZodTypeAny>;

export interface ActivityEventRow {
  id: string;
  companyId: string;
  actorKind: ActorKind;
  actorId: string | null;
  action: ActivityAction;
  entityKind: EntityKind;
  entityId: string;
  agentId: string | null;
  payload: Record<string, unknown>;       // parsed JSON
  createdAt: number;
}
```

**Goal.* defined but not emitted (decisão 2026-05-12):** adiciona os 4 schemas em `ActivityPayloads` sem call sites. M8.5 só plugga — sem migration ou type change. Coerente com "foundation pra M8.5".

## 6. Helper `recordActivity()`

**`apps/main/src/activity/recorder.ts`** (novo):

```ts
export type RecordActivityInput = {
  companyId: string;
  actor: Actor;
  action: ActivityAction;
  entityKind: EntityKind;
  entityId: string;
  agentId?: string | null;                // optional override (default: derived from actor if agent)
  payload: Record<string, unknown>;
};

const MAX_PAYLOAD_BYTES = 4096;

export function recordActivity(db: Database, input: RecordActivityInput): ActivityEventRow {
  // 1. Validate payload shape via Zod schema for input.action
  //    Dev mode (NODE_ENV !== 'production'): throw on unknown action OR shape mismatch.
  //    Prod: log warn + fallback to {} (still write row — audit must remain alive).
  // 2. Serialize payload. If > 4KB:
  //    Dev: throw with explanatory error.
  //    Prod: truncate string fields proportionally + adicionar _truncated: true.
  // 3. Derive agent_id: input.agentId ?? (actor.kind === 'agent' ? actor.id : null).
  // 4. INSERT row (uuid v4 + Date.now()).
  // 5. Broadcast: BrowserWindow.getAllWindows().forEach(w =>
  //      w.webContents.send(IPC.ACTIVITY_NEW, row));
  // 6. Return row (sync — better-sqlite3 prepared statement).
}
```

**Repository** (`apps/main/src/activity/repository.ts`):

```ts
export function insertActivityRow(db: Database, row: ActivityEventRow): void;

export function queryActivity(db: Database, params: {
  companyId: string;
  filters?: {
    actorKind?: ActorKind;
    action?: ActivityAction;
    entityKind?: EntityKind;
    agentId?: string;
    sinceMs?: number;
    untilMs?: number;
  };
  cursor?: { beforeCreatedAt: number; beforeId: string };
  limit?: number;     // default 50
}): ActivityEventRow[];
```

Sem `update` / `delete` por design — append-only ao nível de app, garantia de compliance/audit (alinha §4.11 do spec gaps).

## 8. IPC + real-time

**`packages/shared/src/ipc-channels.ts`** — adicionar:

```ts
ACTIVITY_NEW: 'activity:new',          // main → renderer broadcast
ACTIVITY_QUERY: 'activity:query',      // renderer → main, { companyId, filters, cursor, limit }
```

**`ACTIVITY_NEW` payload** = `ActivityEventRow` único (não array). Renderer filtra client-side via `useActivityStream` — se passa nos filters ativos, prepend; senão drop.

**Handler `activity:query`** em `apps/main/src/ipc/handlers.ts` chama `queryActivity` do repository.

**Granular delta:** broadcast event-por-event, não snapshot. Alinha com refactor que M7.5 PR-C já estabeleceu (IPC delta split + debounce). Não há debounce em `ACTIVITY_NEW` — events são raros o suficiente (não é per-token streaming).

**Animação:** `activity-row-enter` 700ms (fade + slide-down 8px), via CSS keyframes em `apps/renderer/src/index.css`.

## 11. Compliance / audit

Como repositório será público e a app é single-user local:

- **Append-only no nível de app** — repository expõe apenas `insert` + `query`. Sem update/delete.
- **DB backup** — débito já listado em M5 ("Backup automático diário do DB"); quando entrar, `activity_events` vai junto.
- **Sem redaction** — single-user; sem usernames de terceiros pra esconder.
- **`gitleaks` pré-public-push** — já em checklist (memory `project_repo_will_be_public`). Se activity payload acidentalmente logar secret (não deveria, mas se acontecer), `gitleaks` pega.
- **Hard cap 4KB** + `_truncated: true` flag em prod previne crescimento descontrolado.

## 13. Riscos & mitigations

| Risco | Mitigation |
|---|---|
| Volume de `activity_events` cresce demais (DB > 100 MB) | Hard cap 4KB por row. Single-user na prática gera < 1k events/dia. Em 1 ano = ~365k rows × 1KB médio = ~365 MB. Tolerável. Backup automático M5 cobre. |
| Dual-write em transação aborta a operação principal se `recordActivity` falha | Recorder em prod **nunca throws** (warn + fallback). Erro de schema ou size é absorvido. Em dev, throw expõe bug cedo. |
| Action vocab discreto não cobre futuro caso de uso | Adicionar new action requer apenas: (a) string no union, (b) schema em `ActivityPayloads`, (c) i18n strings. Sem migration. |
| Search client-side fica lento com 50k+ rows | V1 só carrega chunks de 50 — search opera sobre o que está em memória. Limite prático: ~5k rows / sessão. FTS5 server-side fica V2. |
| Race condition: row inserida mas broadcast falha → renderer perde event | Renderer fala IPC `activity:query` em mount; reconnect mecanismo natural via re-fetch ao voltar pra rota. Live é melhoria, não fonte de verdade. |
| Backfill retroativo de `issue_events` antigos pedido depois | Não previsto v1. Se vier, script one-shot lê `issue_events` + insere `activity_events` (entity_id preservado). |

## 14. Out-of-scope (V2+)

- **FTS5 server-side** — só se base passar 10k events em single-user (improvável).
- **Cmd+K global search** cross-entity (activities + issues + messages + agents). Lib `cmdk` quando entrar.
- **Dashboard widgets** "Recent Activity (last 10)" + "Active Agents Panel" — M9 consome `activity_events`.
- **Charts/aggregations** de activity (e.g., events por hora) — fora do escopo do stream; M8 traz cost charts.
- **Export CSV/JSON** de activity — não pedido.
- **Edição/redaction** de events — viola append-only.
